# guacamole

![Version: 0.1.0](https://img.shields.io/badge/Version-0.1.0-informational?style=flat-square) ![Type: application](https://img.shields.io/badge/Type-application-informational?style=flat-square) ![AppVersion: 1.6.0](https://img.shields.io/badge/AppVersion-1.6.0-informational?style=flat-square)

Apache Guacamole (webapp + guacd) with PostgreSQL or MySQL backend, built for GitOps.

Deploys the Guacamole web application and `guacd` as separate Deployments and connects them to a
PostgreSQL or MySQL/MariaDB database. All resources are namespaced; one release per namespace is
the intended model for running multiple independent instances.

## Requirements

Kubernetes: `>=1.29.0-0`

## Quick start

```bash
helm upgrade --install guacamole oci://ghcr.io/alirionx/charts/guacamole \
  -n guacamole --create-namespace --wait
```

Every release is also attached to the
[GitHub releases](https://github.com/alirionx/guacamole-helm/releases) as `guacamole-<version>.tgz`
(with `.sha256`).

This deploys Guacamole with an embedded PostgreSQL database. All passwords are generated; the
release notes show how to read the `guacadmin` password.

See [`examples/`](../../examples) for complete values files.

## Deployment paths

The chart behaves the same with the Helm CLI, in CI pipelines, with Argo CD and with Flux; no
feature depends on `lookup`, and rendering is deterministic.

| Tool | Init jobs | Failing init job | Helm test |
|---|---|---|---|
| Helm CLI / pipelines | Helm hooks (`pre-install,pre-upgrade` / `post-install,post-upgrade`) | `helm upgrade --install --wait` fails (`--atomic` rolls back) | `helm test` |
| Argo CD | sync hooks (`PreSync` / `PostSync`) | the sync fails | not used |
| Flux | Helm hooks (helm-controller) | the release fails (remediation per `install`/`upgrade`) | `spec.test.enable: true` |

All four paths are tested against this chart (Argo CD v3.5, Flux v2.9). Examples:

- CLI: [`examples/cli/install.sh`](../../examples/cli/install.sh)
- Pipelines (lint → `helm diff` → deploy): [`examples/pipelines/github-actions.yaml`](../../examples/pipelines/github-actions.yaml), [`examples/pipelines/gitlab-ci.yml`](../../examples/pipelines/gitlab-ci.yml)
- Argo CD: [`examples/gitops/argocd-application.yaml`](../../examples/gitops/argocd-application.yaml); one instance per team with an ApplicationSet: [`examples/gitops/argocd-applicationset.yaml`](../../examples/gitops/argocd-applicationset.yaml)
- Flux: [`examples/gitops/flux-helmrelease.yaml`](../../examples/gitops/flux-helmrelease.yaml)

Under Argo CD the ServiceAccount, Role and RoleBinding of the secret init job remain after a sync
(hook delete policy `BeforeHookCreation`) and are recreated on the next sync.

## Database

`database.type` selects `postgresql` (default) or `mysql` (MySQL and MariaDB).
`database.mode` selects where the database runs:

| Mode | Database server | Database, user, passwords | Tables |
|---|---|---|---|
| `embedded` (default) | StatefulSet of this chart | created automatically | schema init job |
| `external` | provided by you | provided by you | schema init job |

### Embedded database

A single replica StatefulSet with a PersistentVolumeClaim: PostgreSQL 17 for `postgresql`,
MariaDB 11.4 LTS for `mysql`. It is meant to be a solid default, not an enterprise database:
there is no clustering and no backup. High availability and disaster recovery are up to you, e.g.
volume snapshots or a backup tool of your choice; for HA use an external database such as
CloudNativePG.

- Passwords live in the Secret `<fullname>-database` (keys `password` for the application user and
  `superuser-password` for `postgres`/`root`), generated by the secret init job unless
  `database.embedded.existingSecret` is set.
- The webapp and the schema job only use the application user, which owns the Guacamole
  database. The MariaDB `root` user can only log in from inside the database pod.
- The PVC and the generated Secrets are kept on `helm uninstall`; a reinstall picks them up again.
  Delete them manually to start from scratch:
  `kubectl delete pvc,secret -l app.kubernetes.io/instance=<release>`.

#### Database versions and upgrades

The database image is pinned per chart release.

- Chart releases only change the minor/patch version of the embedded database. A new database
  major version requires a new chart major version and a migration as described below.
- PostgreSQL cannot read data of a different major version. An init container compares the
  version of the persisted data with the image and stops with a clear message instead of
  letting the database crash-loop. Fix the image tag and upgrade again; the pod recovers
  automatically.
- MariaDB upgrades its data in place (`MARIADB_AUTO_UPGRADE`).

Migrating PostgreSQL to a new major version (dump/restore):

```bash
kubectl exec <release>-guacamole-database-0 -- pg_dump -U postgres -Fc guacamole > guacamole.dump
# scale down, delete the PVC, upgrade the chart (new major version), then:
kubectl exec -i <release>-guacamole-database-0 -- pg_restore -U postgres -d guacamole --clean --if-exists < guacamole.dump
```

### Preparing an external database

The database user needs permission to create tables in the Guacamole database.

PostgreSQL:

```sql
CREATE USER guacamole WITH PASSWORD '...';
CREATE DATABASE guacamole OWNER guacamole;
```

MySQL / MariaDB:

```sql
CREATE DATABASE guacamole;
CREATE USER 'guacamole'@'%' IDENTIFIED BY '...';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES ON guacamole.* TO 'guacamole'@'%';
```

The schema job uses a database client image: `postgres` for PostgreSQL and
`mariadb` for MySQL/MariaDB (the MariaDB client works with both MySQL and MariaDB servers).
Like the default JDBC mode of the webapp, the MySQL client uses TLS when the server offers it,
without verifying the certificate. Both images can be replaced via `initJobs.schema.*ClientImage`.

## Secrets

The chart never takes passwords as plain values. Every secret is referenced as
`existingSecret` + `secretKey` and passed to the containers via `secretKeyRef`.
Referenced Secrets must be of type `Opaque`.

## Initialization jobs

Two Jobs run as Helm hooks (and as Argo CD sync hooks, so the behavior is identical under the
Helm CLI, CI pipelines, Argo CD and Flux):

| Job | Helm hook | Argo CD hook | Purpose |
|---|---|---|---|
| `<fullname>-secrets-init` | `pre-install,pre-upgrade` | `PreSync` | Verifies referenced Secrets (exist, type `Opaque`, key present) and creates missing chart-managed Secrets with a random value |
| `<fullname>-schema-init` | `post-install,post-upgrade` | `PostSync` | Loads the database schema if it is missing, checks the schema version and secures the `guacadmin` account |

Both jobs are idempotent. A failing job makes `helm install/upgrade --wait` fail.

The secret init job is the only pod that talks to the Kubernetes API. It uses its own ServiceAccount
and a namespaced Role (`create` on Secrets, `get` restricted to the referenced Secret names); all
other pods run without a ServiceAccount token. No password is ever rendered into a manifest, so
rendering is deterministic and no `lookup` is needed.

### Admin password

- Without `auth.admin.existingSecret` the job creates the Secret `<fullname>-admin` with a random
  password. Read it with the command printed in the release notes.
- The password is set on initial schema creation and on later runs only while the default password
  `guacadmin` is still active. A password changed in the web interface is not overwritten.
- `auth.admin.enforcePassword: true` sets the password from the Secret on every install/upgrade,
  e.g. when the Secret is managed by External Secrets or Vault.
- Secrets created by the job are not managed by Helm and are kept on `helm uninstall`. Delete them
  manually when removing the database as well.

### Schema upgrades

Schema upgrade scripts are not applied automatically. If an existing schema is older than the
pinned Guacamole version, the schema job fails with a message naming the required upgrade script
(shipped in the guacamole image under
`/opt/guacamole/extensions/guacamole-auth-jdbc/<database>/schema/upgrade/`). Apply it manually,
then run the upgrade again.

## Authentication

Database authentication is always active: users, connections and permissions live in the
database. Further extensions of the official image are switched on through `auth.*`; the chart
translates them into the image's environment variables and never downloads extensions.

| Values | Purpose |
|---|---|
| `auth.oidc` | OpenID Connect single sign-on |
| `auth.totp` | TOTP as second factor |
| `auth.duo` | Duo (Universal Prompt) as second factor; mutually exclusive with TOTP |
| `auth.extensionPriority` | load order, e.g. `openid` (redirect to the IdP immediately) or `*, openid` (login screen with SSO link) |
| `auth.autoCreateAccounts` | create database accounts for users authenticated by SSO |

### OpenID Connect

Guacamole 1.6 uses the **implicit flow**: the identity provider returns the ID token to the browser,
there is no client secret. Register a public client with the implicit flow (ID token) enabled and
the Guacamole URL as redirect URI. `auth.oidc.redirectUri` defaults to the first Ingress host or
HTTPRoute hostname plus `guacamole.contextPath`.

The browser must reach the authorization endpoint; the Guacamole pod must reach the JWKS endpoint.
Groups from the groups claim are matched against user groups of the same name in Guacamole, so
permissions can be granted per IdP group. Users authenticated by SSO need a database account
(created by an admin or by `auth.autoCreateAccounts`) to store settings such as TOTP keys.

Guacamole rejects ID tokens that are valid for longer than `auth.oidc.maxTokenValidity`
(default 300 minutes). Shorten the token lifetime at the IdP or raise this value.

| IdP | issuer | authorizationEndpoint | jwksEndpoint | Notes |
|---|---|---|---|---|
| Keycloak | `https://<kc>/realms/<realm>` | `<issuer>/protocol/openid-connect/auth` | `<issuer>/protocol/openid-connect/certs` | client authentication off, "Implicit flow" on; "Group Membership" mapper with claim `groups`, full group path off; `usernameClaim: preferred_username` |
| Microsoft Entra ID | `https://login.microsoftonline.com/<tenant>/v2.0` | `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/authorize` | `https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys` | app registration: Web redirect URI, "ID tokens (used for implicit and hybrid flows)" on; groups claim via "Token configuration" (contains group object IDs) |
| Authentik | `https://<authentik>/application/o/<slug>/` | `https://<authentik>/application/o/authorize/` | `https://<authentik>/application/o/<slug>/jwks/` | OAuth2/OpenID provider with client type "Public"; groups in claim `groups` |
| Dex | `issuer` of the Dex config | `<issuer>/auth` | `<issuer>/keys` | `oauth2.responseTypes: [code, token, id_token]`; scope `openid email profile groups`; Dex ID tokens are valid for 24h by default: set `expiry.idTokens` (e.g. `1h`) or `auth.oidc.maxTokenValidity: 1440` |

The Dex variant is covered by the integration test of this chart (login, group claim, automatically
created accounts). See `examples/oidc-keycloak-totp.yaml` for a complete example.

### TOTP and Duo

- **TOTP**: users enroll on their first login (QR code); keys are stored in the database.
- **Duo**: create a "Web SDK" application in Duo and store its client secret in an Opaque Secret
  (`auth.duo.existingSecret`, key `client-secret`). `auth.duo.redirectUri` is derived like the OIDC
  redirect URI.
- Both support `bypassHosts`/`enforceHosts` (IPs/CIDRs). They depend on the correct client IP; behind
  a proxy this requires the RemoteIpValve (see [Client IP behind a proxy](#client-ip-behind-a-proxy)).

## Additional extensions and properties

Official extensions are part of the image and enabled through `auth.*` only. For other extensions,
`guacamole.extraExtensions` takes a list of entries with exactly one source each:

| Source | How it works | Requirements |
|---|---|---|
| `image` (recommended) | an init container copies all `*.jar` from `path` (default `/extensions`) of the image | the image contains `/bin/sh` and `cp` (e.g. `FROM busybox`), world-readable JARs; `imagePullSecrets` per entry |
| `url` | an init container (guacamole image) downloads the JAR and verifies `sha256`; the pod does not start on a mismatch | `sha256` is mandatory; with NetworkPolicies allow the download via `networkPolicy.guacamole.extraEgress` |
| `imageVolume` | the directory `path` (default `extensions`) of an image is mounted as `GUACAMOLE_HOME/extensions`, no init container | Kubernetes image volumes supported by cluster and container runtime; must be the only entry, since container runtimes only mount directories from image volumes |

The JARs end up in the template `GUACAMOLE_HOME` (`/etc/guacamole/extensions`); the image's
entrypoint links them into the generated home next to the official extensions it enables from
environment variables, so both coexist. Only JARs directly in that directory are loaded. Do not
provide the same extension twice (e.g. an official one that is also enabled via `auth.*`): the
webapp fails to start.

Example image (`examples/extension-image/Dockerfile`):

```dockerfile
FROM busybox:1.36
COPY --chmod=0644 my-guacamole-extension-1.0.0.jar /extensions/
```

Alternatively, build your own image `FROM guacamole/guacamole` and set `guacamole.image`.

`guacamole.extraProperties` adds entries to `guacamole.properties` (e.g. `api-session-timeout`),
and `guacamole.extraEnv` adds environment variables, for options the chart does not model.

## Exposure

Guacamole is served at `guacamole.contextPath` (default `/`). It can be exposed in three ways,
which may be combined:

| Option | Values | TLS |
|---|---|---|
| Service | `guacamole.service.type`: `ClusterIP` (default), `NodePort`, `LoadBalancer` | — |
| Ingress | `ingress.enabled` | `ingress.tls.enabled` + `secretName` (e.g. issued by cert-manager) |
| Gateway API | `httpRoute.enabled` + `parentRefs` of an existing Gateway | terminated at the Gateway's HTTPS listener; optional HTTP→HTTPS redirect route (`httpRoute.httpsRedirect`) |

The chart never creates a Gateway: listeners and certificates belong to whoever operates the
Gateway. Attach the route to the HTTPS listener via `sectionName`.

### WebSocket and timeouts

Guacamole sessions run over a long-lived WebSocket tunnel (`/websocket-tunnel`). Proxies must
allow the upgrade and must not cut idle connections too early.

- **Traefik**: WebSockets work out of the box (tested with Traefik v3 for Ingress and Gateway API).
- **Gateway API**: `httpRoute.timeouts` sets the rule timeouts; check the defaults of your
  implementation for idle/stream timeouts.

### Sticky sessions

With more than one webapp replica, all requests of a session must reach the same pod.

- LoadBalancer Service: `guacamole.service.sessionAffinity: ClientIP`.
- Traefik: Service annotation `traefik.ingress.kubernetes.io/service.sticky.cookie: "true"`
  (via `guacamole.service.annotations`, see `examples/ingress-tls.yaml`).
- Gateway API: session persistence is not part of the standard channel yet; use the policy or
  annotation of your implementation.

### Client IP behind a proxy

Tomcat's RemoteIpValve takes the client IP and protocol from `X-Forwarded-For` /
`X-Forwarded-Proto`. It is enabled automatically when `ingress` or `httpRoute` is enabled
(`guacamole.remoteIpValve.enabled: null`), so that logs and the brute-force protection of the
ban extension see the real client IP. Headers are only trusted from private IP ranges unless
`guacamole.remoteIpValve.internalProxies` says otherwise. Keep the valve disabled when clients
connect directly, e.g. through a LoadBalancer Service, since they could spoof the header.

### Fixed load balancer IP

`spec.loadBalancerIP` is deprecated in Kubernetes and therefore not supported. Request a fixed IP
through the annotation of your load balancer implementation:

```yaml
guacamole:
  service:
    type: LoadBalancer
    annotations:
      metallb.io/loadBalancerIPs: "192.168.1.10"   # MetalLB
      # lbipam.cilium.io/ips: "192.168.1.10"       # Cilium LB IPAM
```

## Security

All pods (webapp, guacd, embedded database, init jobs) run as non-root with a read-only root
filesystem, no capabilities, no privilege escalation and the `RuntimeDefault` seccomp profile, and
are compatible with the Pod Security Standard `restricted`. Only the secret init job mounts a
ServiceAccount token. Kubernetes service links are disabled because the official image enables
extensions based on environment variable prefixes.

### NetworkPolicies

`networkPolicy.enabled: true` creates a default-deny policy per component that only allows:

| Pod | Ingress | Egress |
|---|---|---|
| webapp | port 8080 from `networkPolicy.guacamole.from` (empty: all sources) | DNS, guacd, database, `networkPolicy.guacamole.extraEgress` |
| guacd | port 4822 from the webapp | DNS, `networkPolicy.guacd.egressTo` (empty: everything) |
| embedded database | database port from the webapp and the schema job | none |
| schema init job | none | DNS, database |
| secret init job | none | DNS, Kubernetes API (`networkPolicy.kubeApiServer`) |

- Set `networkPolicy.guacamole.from` to the namespace of your ingress controller or Gateway.
- With OIDC or Duo, allow the webapp to reach the identity provider's JWKS endpoint or the Duo API
  via `networkPolicy.guacamole.extraEgress`, otherwise logins fail.
- Restrict `networkPolicy.guacd.egressTo` to the networks and ports of your remote desktop targets:
  guacd connects wherever a connection points to.
- For an external database, `networkPolicy.database.externalTo` narrows the destination.
- The policies need a CNI that enforces NetworkPolicies.

## Availability and scaling

- `guacamole.podDisruptionBudget` / `guacd.podDisruptionBudget` create PodDisruptionBudgets
  (default `maxUnavailable: 1`). With a single replica, `minAvailable: 1` blocks node drains.
- `guacamole.autoscaling` / `guacd.autoscaling` create HorizontalPodAutoscalers (CPU and/or memory
  utilization, optional `behavior`) and replace `replicaCount`; they require metrics-server. More
  than one webapp replica requires sticky sessions (see [Sticky sessions](#sticky-sessions)).
- The embedded database always runs as a single replica.
